# HPFA Lindy + Pareto Roadmap V1

Status: `POLICY_CORRECTION_PASS`

## Operating premise

HPFA optimizes for two things at the same time:

```text
VERİM = safe analyst value per unit of complexity
ÇEŞİTLİLİK = multiple independent evidence routes, methods and interpretations
```

Pareto decides what to do first.
Lindy decides what is likely to remain valuable for a long time.

The combined rule is:

```text
Build the smallest durable core that supports the widest safe analytical variety.
```

## Imaginary interview: How would the top 0.01% build HPFA?

### Interviewer

You have unlimited ideas, multiple donor repositories, many candidate metrics, and a growing intelligence stack. What do you build first?

### Top 0.01% Builder

We do not begin with the most exciting feature. We begin with the most reusable constraint.

The durable order is:

```text
source authority
canonical identity
failure propagation
shared contracts
tests
provenance
composition
argument
language
release
```

A system that cannot preserve identity, propagate failure, or explain provenance is not intelligent. It is only expressive.

### Interviewer

What is the biggest mistake a highly ambitious analytics project makes?

### Top 0.01% Builder

It confuses variety with accumulation.

Real variety means:

```text
multiple evidence families
multiple temporal scales
multiple spatial views
multiple counter-explanations
multiple disciplines
multiple routes to abstention
```

Fake variety means:

```text
hundreds of disconnected metrics
many report templates
many readers with no consumers
many graphs with no contract
```

We want diversity of reasoning, not diversity of clutter.

### Interviewer

How do you use donor repositories?

### Top 0.01% Builder

We never ask, “What can we copy?”

We ask:

```text
What product gap exists in hpfa?
Which donor has the strongest proven primitive for that gap?
What is the smallest HPFA-native contract that captures the value?
Which tests prove the adaptation?
Which downstream modules benefit?
```

A donor capability must create leverage across the main product. Otherwise it stays reference-only.

### Interviewer

How do you decide whether a new metric deserves implementation?

### Top 0.01% Builder

A metric is not valuable because it is sophisticated.

It is valuable if it changes one of these:

```text
argument eligibility
counter-evidence strength
context interpretation
uncertainty estimate
analyst decision
```

If it does none of those, it is probably decorative.

### Interviewer

What would you do with the current Intelligence Layer?

### Top 0.01% Builder

Stop adding nodes for a moment.

Make the existing chain trustworthy:

```text
Packet
-> Fusion
-> Argument
-> Defeasible Route
-> Evidence Graph
-> Lens Matrix
-> Safe Sentence
-> Report Block
-> Output Contract
-> Assembly Gate
```

Then prove one thing:

```text
A real upstream artifact can move through the whole chain unchanged in identity,
without bypassing failure states,
without leaking forbidden outputs,
and without inflating release status.
```

That proof is worth more than ten new modules.

### Interviewer

How do you keep the system alive for years?

### Top 0.01% Builder

We favor Lindy components:

```text
plain contracts
stable identifiers
append-only registries
simple state vocabularies
explicit provenance
small deterministic functions
text and JSON outputs
regression tests
fail-closed gates
```

We are cautious with fragile components:

```text
opaque scoring
hardcoded thresholds
model-specific assumptions
untraceable embeddings
provider-specific field names
monolithic orchestrators
```

The more a component has survived across providers, seasons and modules, the more central it may become.

### Interviewer

How do you balance efficiency and variety?

### Top 0.01% Builder

We create a narrow core and a wide edge.

Narrow core:

```text
identity
authority
contracts
failure states
provenance
claim ceilings
```

Wide edge:

```text
statistics
entropy
graph theory
geometry
Bayesian updates
game theory
sequence motifs
rhythm diagnostics
contradiction patterns
```

The core stays small and stable.
The analytical edge can grow safely because every method must pass through the same core.

### Interviewer

What do you refuse to build?

### Top 0.01% Builder

Anything that creates the appearance of intelligence without increasing verifiability.

Examples:

```text

new metrics without argument consumers
knowledge graph without stable node identity
orchestrator before failure propagation is complete
claim language before counter-evidence routing
```



```text

```

## Healthy roadmap

## Phase 0 — Repository hygiene and branch truth

Goal: one understandable product state.

Actions:

```text
classify every open PR as MERGE / REBASE / SUPERSEDED / CLOSE
close stale documentation-only branches that no longer match main
keep only current product work visible
publish one current-main capability inventory
```

Exit condition:

```text
no ambiguous open PR remains
```

## Phase 1 — Durable integration core

Goal: make the current Intelligence Layer trustworthy.

Order:

```text
1. Packet -> Fusion failure propagation
2. shared recursive forbidden-field scan
3. canonical Argument -> Defeasible Route -> Evidence Graph contract
4. standard decision/state vocabulary audit
5. end-to-end Intelligence Chain fixture
```

Exit condition:

```text
one synthetic match-agnostic artifact traverses the full chain
all upstream failures stop downstream execution
canonical_event_count remains UNKNOWN
no forbidden nested output survives
```

## Phase 2 — Intelligence Pipeline Orchestrator Lite

Goal: run existing modules as one auditable product path.

The orchestrator must remain thin.

It may:

```text
call stages
record inputs and outputs
stop on block
stop or hold on review
write stage ledger
preserve identities
```

It may not:

```text
invent evidence
repair invalid upstream records silently
promote release states
create tactical truth
```

Exit condition:

```text
complete engineering ledger for one full candidate chain
```

## Phase 3 — Contradiction Candidate Engine

Goal: improve reasoning diversity, not metric count.

Initial families:

```text
access vs terminal production
volume vs quality surface
progression vs loss exposure
recovery vs subsequent progression
restart dependence vs open-play production
territory vs shot conversion
```

Outputs:

```text
qualifier candidate
explicit contradiction candidate
counter-scenario candidate
insufficient comparability
```

Exit condition:

```text
counter-evidence can weaken or withdraw an argument through the canonical pipeline
```

## Lindy priority rules

Prefer:

```text
simple deterministic transformations
stable schemas
append-only registries
explicit state machines
portable text/JSON/TSV artifacts
small composable modules
provider-neutral contracts
```

Delay or isolate:

```text
opaque learned scores
provider-specific shortcuts
hardcoded match identities
single-signal state assignment
large monolithic runners
untraceable automatic language
```

## Pareto priority rules

DO_NOW:

```text
work that closes a cross-module blocker
work that protects many downstream modules
work that prevents false analyst output
work that creates reusable infrastructure
```

DO_NEXT:

```text
work enabled by the current blocker closure
```

DEFER:

```text
valid but isolated metrics or visualizations
```

REJECT:

```text
duplicate capability
unsupported truth production
non-portable hardcoding
no downstream consumer
```

```text
3. unify recursive forbidden scans
4. declare canonical defeasible route
5. add one end-to-end chain test
```

These five actions unlock most of the value already built into the Intelligence Layer.
